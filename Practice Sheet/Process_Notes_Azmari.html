1
What is a Process?
A process is a program that is in execution. But it is more than just the code — it is code + data + current execution state.

Early computers allowed only one program at a time. Modern systems load multiple programs concurrently. This evolution gave rise to the concept of a process — the fundamental unit of work in a modern OS.

ℹ️ The terms "job" and "process" are used almost interchangeably in OS literature (e.g., "job scheduling" = "process scheduling").
🍳 Real-Life Example — Cooking Analogy
  • Recipe = Program (just a list of instructions, passive, stored on paper/disk)
  • Cooking = Process (the actual execution of those instructions)

While cooking you have: which step you are on, the ingredients (data), and temporary notes (stack). That is exactly what a process contains!

① Text Section (Code)

The executable code of the program — instructions written in C/C++ etc. This section is fixed in size and does not change during runtime.

🍳 Analogy

The recipe instructions themselves — they don't change.

② Data Section

Stores global variables — declared outside functions, and exist for the entire program lifetime. Fixed size.

🍳 Analogy

Permanent ingredients you always use (salt, oil).

③ Heap Section

Memory dynamically allocated during runtime (via malloc, new). Grows upward. Must be managed carefully.

🍳 Analogy

Buying extra ingredients while cooking — flexible but needs management.

④ Stack Section

Stores temporary data: function call parameters, local variables, and return addresses. Grows downward. Each function call pushes an activation record; returning pops it.

🍳 Analogy

A notepad while cooking — used temporarily and erased after use.

Program Counter & Registers

Besides the memory sections, the OS tracks two critical CPU state elements per process:

  • Program Counter (PC) — holds the address of the next instruction to execute.
  • CPU Registers — store current working values (accumulators, index registers, stack pointers, general-purpose registers, condition codes).
🍳 Analogy

PC = "Which step of the recipe are you on?"
Registers = "What are you currently holding in your hands?"

⚠️ The sizes of text and data sections are fixed. Stack and heap sections can shrink and grow dynamically. The OS must ensure they do not overlap each other.

Process = Code + Current Execution + Memory (stack, heap, data)

3
Program vs. Process

Program

  • Passive entity
  • Stored on disk as an executable file
  • Just a list of instructions
  • Does not change

Process

  • Active entity
  • Loaded into memory, currently executing
  • Has a program counter + resources
  • Has dynamic data, heap, stack
💡 Key Point: One program can give rise to many processes. For example, opening three browser windows = three separate processes, each sharing the same code (text section) but having different data, heap, and stack.

A program becomes a process when its executable file is loaded into memory — triggered by double-clicking, running a command, etc.

4
Process Control Block (PCB)

Each process is represented in the OS by a Process Control Block (PCB), also called a Task Control Block. The PCB is a data structure that stores all information about a process.

PCB
Process State
Process Number (PID)
Program Counter
CPU Registers
CPU Scheduling Info
Memory-Management Info
Accounting Information
I/O Status Information

Fields Explained:

  • Process state — new, ready, running, waiting, terminated
  • Program counter — next instruction address
  • CPU registers — all register contents (must be saved on interrupt)
  • CPU scheduling info — priority, queue pointers, parameters
  • Memory-management info — base/limit registers, page tables
  • Accounting info — CPU time used, time limits, account numbers
  • I/O status info — I/O devices allocated, list of open files
✅ In brief, the PCB serves as the repository for all data needed to start, or restart, a process — along with accounting data.

PCB in Linux

In Linux, each process is represented by the C structure task_struct (in <include/linux/sched.h>):

pid_t pid;               /* process identifier */
long state;              /* state of the process */
unsigned int time_slice; /* scheduling information */
struct task_struct *parent; /* this process's parent */
struct list_head children;  /* this process's children */
struct files_struct *files; /* list of open files */
struct mm_struct *mm;    /* address space of this process */

All active processes form a doubly linked list of task_struct. The kernel maintains a pointer current pointing to the currently executing process.

5
States of a Process

A process doesn't just run continuously — it moves through different states during its life. The state defines the current activity of the process.

🎓 Real-Life Example — Student in Exam Hall

Think of a student taking an exam. Each stage of the exam maps to a process state:

🆕

New

Process is being created. Not started yet.

Student enters exam hall, gets question paper.

✋

Ready

Ready to run, waiting for CPU assignment.

Student ready to write, waiting for teacher's signal.

✍️

Running

Instructions are being executed. Actively using CPU.

Student is writing answers.

⏳

Waiting

Waiting for an event (I/O, resource). Cannot run even if CPU is free.

Student pauses — waiting for extra paper.

🏁

Terminated

Process has finished execution.

Student submits paper and leaves the hall.

6
Process Scheduling
Process Scheduling = the OS decides which process runs next on the CPU core.

The process scheduler selects among available processes for the next execution on a CPU core. Goals: maximize CPU use, quickly switch processes onto CPU.

👩‍🏫 Real-Life Example — Teacher and Students
  • Teacher = CPU
  • Students = Processes

Only one student can speak at a time. The teacher decides: who speaks next, and for how long. That is process scheduling.

Scheduling Queues

The OS organizes processes into queues:

Ready Queue

All processes residing in main memory, ready and waiting to execute. Waiting for CPU assignment.

Like students with hands raised, waiting to speak.

Wait Queue(s)

Processes waiting for an event to occur (e.g., I/O completion, child termination, interrupt).

Like students waiting for a book or permission.

Processes migrate continuously among queues: Ready → Running → Waiting → Ready → Running → ...

Types of Process Behavior

  • I/O-bound process — spends more time doing I/O than computation; frequent short CPU bursts.
  • CPU-bound process — generates I/O requests infrequently; uses more time computing.
ℹ️ The number of processes currently in memory is called the degree of multiprogramming.
7
Context Switch
A Context Switch occurs when the CPU switches from one process to another. The OS saves the state of the current process and loads the saved state of the next process.

What is "Context"?

The context of a process is its current state, stored in the PCB. It includes:

  • Program Counter (next instruction)
  • CPU Register values
  • Memory-management information
  • Execution point / process state

Context Switch Steps

① Save old process state → PCB₀
→
② Load new process state from PCB₁
→
③ New process runs
👩‍🏫 Real-Life Example — Switching Students

Teacher stops Student A mid-answer and calls on Student B:

  1. Writes down where Student A stopped (saves context).
  2. Calls Student B (loads new context).
  3. Later returns to Student A from the exact same point.

That's context switching!

Context Switch Overhead

⚠️ Context switch time is pure overhead — the system does NO useful work while switching. The more complex the OS/PCB, the longer the context switch takes.

Factors affecting context-switch time:

  • OS complexity and PCB size
  • Number of registers to copy
  • Hardware support — some CPUs have multiple register sets, making switching much faster (just change a pointer to the current register set)
  • Memory-management technique used

A typical context switch takes several microseconds.

8
Dual Mode Operation

The OS needs to distinguish between execution of OS code and user-defined code. This is done using dual mode operation.

🏦 Real-Life Example — Bank System

User Mode (Customer Area): You can deposit, withdraw, check balance — but you CANNOT open the vault, change bank rules, or access other accounts directly.

Kernel Mode (Bank Staff / Manager Area): Employees can open the vault, approve large transactions, access all records, fix system issues.

User Mode (mode bit = 1)

  • Programs like Chrome, VS Code, your C program run here
  • Cannot directly access hardware (CPU, memory, disk)
  • Cannot execute privileged/dangerous instructions
  • Limited, safe, restricted environment

Why? To prevent crashes or hacking.

Kernel Mode (mode bit = 0)

  • Operating System (Windows, Linux kernel) runs here
  • Can access hardware directly
  • Can manage memory, control processes
  • Full access, controls the whole system

Privileged instructions only execute here.

Mode Bit

  • 0 → Kernel mode (full power)
  • 1 → User mode (limited access)

A mode bit is added to the computer hardware. The CPU constantly checks this bit: "Is this instruction allowed right now?"

How They Work Together

⚠️ Dual mode exists because if user programs had full access, they could crash the OS, corrupt memory, or hack the system — just like customers opening the bank vault would cause chaos.
9
System Calls
A System Call is a way for a user program to request a service from the OS. It is the bridge between the user program and the OS kernel.

User programs run in user mode (limited). When they need something important (like reading a file), they cannot do it directly — they must request the OS. That request = System Call.

🍽️ Real-Life Example — Restaurant
  • You (user program) — want food (a service) but can't go into the kitchen
  • Kitchen (OS) — has full access to everything, prepares food safely
  • Waiter (System Call) — takes your request to the kitchen and brings back the result

Waiter = System Call!

Example in Computer

printf("Hello");

Internally: Your program (user mode) wants to print text → it cannot directly access the screen → it makes a system call → OS (kernel mode) prints it.

10
System Call Interface
The System Call Interface (SCI) is the mechanism that connects a program to the correct system call inside the OS — a dispatcher or router.
📞 Real-Life Example — Call Center
  • You (program) — call customer service and say "I want to check my balance"
  • Call Operator (SCI) — checks a code/number, routes you to the right department
  • Department (OS Kernel) — performs the actual work and sends back the result

How System Call Numbers Work

Each system call has a unique number. Example:

  • 1 → write
  • 2 → read
  • 3 → open

Your program doesn't directly call "write" — it sends a number, and the SCI finds it in a lookup table.

Step-by-Step Flow

  1. Program calls an API function (e.g., printf)
  2. API prepares a system call number
  3. Control passes to the System Call Interface
  4. SCI looks up the number in its table → finds correct OS function
  5. OS executes in kernel mode
  6. Result is returned back to the program
ℹ️ Key Points:
• "Caller need not know implementation" — you just call the function; OS handles details.
• "API hides details" — simple functions hide complex OS operations.
• "Run-time support library" — libraries bundled with compiler (like C standard library) provide API functions (printf, scanf) and handle system call interaction.
💡 Memory Trick
  • API → Easy for programmer
  • SCI → Connects using numbers
  • Kernel → Does real work
11
Process Creation

The process that creates another is called the parent; the created process is the child. Children can create more children — forming a tree of processes.

👨‍👩‍👧 Real-Life Example — Family Tree

Grandparent → Parent → Child → Grandchild — same structure as a process tree!

Process Identifier (PID)

Every process gets a unique integer ID (PID). The OS uses PID to track and manage processes.

systemd (PID=1) ├── logind (PID=8415) │ └── bash (PID=8416) │ ├── ps (PID=9298) │ └── vim (PID=9204) └── sshd (PID=3028) └── sshd (PID=3610) └── tcsh (PID=4005)

Typical Linux process tree. systemd (always PID=1) is the root parent of all user processes, created first when the system boots.

Resource Sharing Options

Share ALL Resources

Parent & child share memory, files, variables. Fast but risky.

Like a family sharing one bank account.

Share SOME Resources

Child gets a subset of parent's resources. Most common.

Parent gives pocket money, not full bank access.

Share NO Resources

Parent and child completely independent. Safe, no cooperation.

Two strangers — no shared resources.

Execution Options

Run Concurrently

Parent and child run at the same time. Multitasking.

Parent downloading file, child playing music.

Parent Waits

Parent stops until child finishes. Used when result is needed.

Parent waits for child to complete task.

Process Creation in UNIX — fork(), exec(), wait()

  • fork() — creates a new child process (copy of parent's address space). Returns 0 to child, child's PID to parent, <0 on error.
  • exec() — replaces process memory space with a new program (child overlays itself with a new executable).
  • wait() — parent suspends execution until one of its children terminates; receives child's PID and exit status.
#include <sys/types.h>
#include <stdio.h>
#include <unistd.h>

int main() {
    pid_t pid;
    pid = fork();           /* fork a child process */

    if (pid < 0) {          /* error occurred */
        fprintf(stderr, "Fork Failed");
        return 1;
    }
    else if (pid == 0) {    /* child process */
        execlp("/bin/ls", "ls", NULL);
    }
    else {                  /* parent process */
        wait(NULL);         /* parent waits for child to complete */
        printf("Child Complete");
    }
    return 0;
}

How fork() Works — Visualization

Parent Process (PID 100) | fork() | ────────────────── | | Child (PID=0) Parent (PID=101) Runs exec() Calls wait(), then resumes
ℹ️ In Windows, process creation uses CreateProcess(), which requires loading a specified program into the child's address space at creation time (at least 10 parameters needed, unlike fork()'s zero parameters).
12
Process Termination

A process terminates when it finishes executing its final statement and is removed from memory.

Normal Termination — exit()

exit(status);

Process completes its last instruction → calls exit() → sends a status (result) to its parent → all resources (memory, open files, I/O buffers) are deallocated by OS.

🎓 Analogy

Student completes exam → submits paper (status) → leaves the hall.

Parent Collects Result — wait()

pid = wait(&status);

Parent can use wait() to pause until a child finishes, then receive the child's PID and exit status.

Forced Termination — abort()

A parent can terminate a child process using abort(). Reasons:

  • Child has exceeded its allocated resources
  • Task assigned to child is no longer required
  • Parent is exiting (and OS doesn't allow orphans)
🎓 Analogy

"Stop playing, go to sleep!" — Parent forcibly stops child.

Cascading Termination

If a parent terminates, all its children must also terminate (in systems that don't allow orphans). This is called cascading termination, initiated by the OS.

Parent ├── Child1 │ └── Grandchild └── Child2 If Parent terminates → Child1, Child2, Grandchild ALL terminate.

Zombie Process

A process that has terminated but whose parent has NOT called wait(). The OS still keeps its PID and exit status in the process table.

🎓 Analogy

Student finished exam, but teacher didn't collect the paper. Student is gone, but the record still exists. That's a zombie!

Orphan Process

A process whose parent died before the child finished. The OS re-assigns the child to another process (in Linux/UNIX: init or systemd, PID=1), which periodically calls wait().

🎓 Analogy

Child loses parent. A guardian (init/systemd) adopts the child.

Summary Table

TypeSituation
Normal TerminationChild finishes using exit(), parent collects via wait()
Forced TerminationParent kills child using abort()
ZombieChild finished, parent did NOT call wait()
OrphanParent died before child finished; child adopted by init/systemd
💡 Memory Trick
  • exit → finish
  • wait → collect
  • no wait → zombie
  • no parent → orphan

Interprocess Communication (IPC)

Processes running concurrently may be independent (cannot affect each other) or cooperating (can affect or be affected by each other). Cooperating processes need IPC.

Why Process Cooperation?

  • Information sharing — multiple applications may need the same data (e.g., copy-paste)
  • Computation speedup — break a task into parallel subtasks (needs multiple cores)
  • Modularity — divide system functions into separate processes/threads
  • Convenience — user multitasking
IPC (Interprocess Communication) = a mechanism to exchange data and information among cooperating processes. Two fundamental models: Shared Memory and Message Passing.
💡 Real-Life Example — Two People in Different Rooms

They can communicate in two ways:

  1. Share a whiteboard — both read/write on it (Shared Memory)
  2. Send messages — chat/WhatsApp/SMS (Message Passing)

① Shared Memory

A region of memory shared by cooperating processes. Both can read and write to it.

🖊️ Analogy

Two people sharing a whiteboard — one writes, other reads.

Advantages:

  • Very fast (no data copying, no kernel intervention after setup)
  • Good for large amounts of data

Disadvantage:

  • Needs synchronization — if both write at same time, data gets corrupted

② Message Passing

Processes send and receive messages; no shared memory needed. A communication link must exist.

Process P → send(message) → Process Q
Process Q → receive(message)
💬 Analogy

Person A sends WhatsApp message; Person B receives it.

Advantages:

  • Safe — no shared memory conflict
  • Easier to implement in distributed systems

Disadvantage:

  • Slower — requires kernel intervention (system calls)
  • Not efficient for large data

Comparison Table

FeatureShared MemoryMessage Passing
SpeedFast (no kernel after setup)Slower (each msg = system call)
Data sizeGood for large dataGood for small data
ComplexityNeeds synchronizationSimpler
Use caseSame machine / systemDistributed systems

Producer-Consumer Problem (Shared Memory Example)

A classic example: Producer produces items → places in a shared buffer → Consumer reads and consumes.

  • in = next free position in buffer
  • out = first full position in buffer
  • Buffer is full when (in+1) % BUFFER_SIZE == out
  • Buffer is empty when in == out
💡 Memory Trick
  • "Share → Shared Memory"
  • "Send → Message Passing"

Practice: fork() Problems
ℹ️ Key Rules for fork():
• Each fork() doubles the number of processes.
• fork() returns 0 to the child, child's PID (>0) to parent, <0 on error.
• Both parent and child continue from the line after the fork.
• Each process has its own copy of all variables.

Problem 1

main(){
    fork();   // 2 processes
    fork();   // 4 processes
    printf("hi\n");   // 4 "hi"
    fork();   // 8 processes
    printf("hello\n"); // 8 "hello"
    fork();   // 16 processes
    printf("bye\n");   // 16 "bye"
}
Output: 4 × "hi", 8 × "hello", 16 × "bye"

Problem 2

main(){
    fork();        // 2 processes
    fork();        // 4 processes
    c = fork();    // 8 processes
    if(c > 0){     // 4 parents print "hi" and fork again → 8 more
        printf("hi\n");
        fork();
    }
    fork();        // all print "bye"
    printf("bye\n");
}

Problem 3 (Variable Values)

int main(){
    pid_t p;
    int a=3, b=11;
    char s[20];
    p = fork();
    if(p < 0)  { printf("fork failed\n"); }
    else if(p == 0) {            /* CHILD */
        strcpy(s, "child");
        a = a * b;   // a = 3*11 = 33
        b = b / a;   // b = 11/33 = 0
    }
    else {                       /* PARENT */
        wait();
        strcpy(s, "parent");
        a = a + b;   // a = 3+11 = 14
        b = b - a;   // b = 11-14 = -3
    }
    printf("%s is printing a= %d\n", s, a);
    printf("%s is printing b= %d\n", s, b);
    return 0;
}
Child output: a = 33, b = 0
Parent output: a = 14, b = -3

Problem 4 (Static Variables)

static int a=5, b=3;
int main(){
    pid_t x, y;
    x = fork();
    if(x > 0){         /* FIRST PARENT */
        a=a+5; b=b-5;  // a=10, b=-2
        wait();
        y = fork();
        if(y > 0){     /* GRANDPARENT */
            wait();
            a=a-2; b=b+2;  // a=8, b=0
        }
        else{          /* SECOND CHILD */
            a=a*2; b=b/3;  // a=20, b=-2/3=0
        }
    }
    else{              /* FIRST CHILD */
        a=a/2; b=b*3;  // a=2, b=9
    }
    printf("a=%d\n",a);
    printf("b=%d\n",b);
    return 0;
}
First Child: a=2, b=9
Second Child (y==0): a=20, b=0
Grandparent (y>0): a=8, b=0
